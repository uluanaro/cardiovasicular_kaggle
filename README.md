# Прогнозирование сердечно-сосудистых заболеваний

End-to-end проект классического машинного обучения: от сырых медицинских данных
до работающего REST-сервиса, выдающего оценку риска сердечно-сосудистого
заболевания по показателям пациента.

Акцент проекта — не на «погоне за метрикой», а на **обоснованности каждого
решения**: почему именно такая очистка, такие признаки, такая метрика, такой
порог и такая модель. Все ключевые выборы объяснены ниже в разделах «почему так».

---

## 1. Задача и данные

- **Задача:** бинарная классификация — есть у пациента сердечно-сосудистое
  заболевание (`cardio = 1`) или нет (`cardio = 0`).
- **Датасет:** [Cardiovascular Disease dataset (Kaggle)](https://www.kaggle.com/datasets/sulianova/cardiovascular-disease-dataset),
  ~70 000 записей, разделитель `;`.
- **Главная метрика:** **recall** по классу «болен» (обоснование — в разделе 6),
  в паре с **ROC-AUC** для сравнения моделей.

**Признаки на входе** (как их собирают при обследовании):

| Признак | Описание |
|---|---|
| `age` | возраст в днях |
| `gender` | пол (1 / 2) |
| `height`, `weight` | рост (см), вес (кг) |
| `ap_hi`, `ap_lo` | верхнее / нижнее артериальное давление |
| `cholesterol`, `gluc` | холестерин и глюкоза (1 — норма, 2 — выше нормы, 3 — сильно выше) |
| `smoke`, `alco`, `active` | курение, алкоголь, физическая активность (0 / 1) |

Целевая переменная — `cardio`. Столбец `id` удалён как неинформативный.

---

## 2. Очистка данных

Главная особенность датасета — грязь представлена **не пропусками (NaN), а
физически невозможными значениями** в заполненных ячейках (отрицательное давление,
давление в тысячи единиц, рост 50 см, вес 10 кг). Такую грязь `dropna()` не ловит —
она видна только через `describe()` по `min`/`max` и по аномально большим `std`.

Чистка выполнена по **доменным (медицинским) границам**:

| Правило | Оставляем |
|---|---|
| `ap_hi` | 90–200 |
| `ap_lo` | 60–130 |
| `ap_lo < ap_hi` | обязательно (иначе ошибка ввода — перепутаны поля) |
| `height` | 120–220 см |
| `weight` | 30–200 кг |

Результат: **70 000 → 68 331 строк (удалено ~2.4 %)** — ожидаемая доля брака,
сигнал не затронут.

**Почему доменные границы, а не процентили.** Высокое давление — это и есть наш
главный предиктор: гипертоники чаще болеют. Процентильная обрезка (срезать верхние
N %) выбросила бы настоящих тяжёлых пациентов вместе с опечатками и уничтожила бы
сигнал. Доменная граница отличает «190 — реальный больной» от «11000 — опечатка»,
процентиль — нет. На медицинских данных чистят по физиологии, а не по статистике.

## 3. Конструирование и отбор признаков

**Созданные признаки:**

- `age_years = age / 365` — читаемый возраст вместо дней.
- `bmi = weight / (height / 100)²` — индекс массы тела. Рост переводится в метры
  (деление на 100), иначе формула даёт мусор.

**Почему BMI, а не рост и вес по отдельности.** Медицина связывает риск именно с
отношением вес/рост². Готовый признак вкладывает в модель это знание; особенно
важно для линейных моделей (логистическая регрессия физически не умеет сама
поделить вес на квадрат роста), и повышает интерпретируемость.

**Новая грязь от сконструированного признака.** После расчёта BMI обнаружились
значения 10.7 и 108 — хотя рост и вес по отдельности прошли фильтр, их
**комбинация** дала бред. Урок: новый признак нужно проверять заново. BMI
дополнительно ограничен коридором **15–60** (−0.06 %).

**Отбор признаков.** Из обучающей матрицы убраны `age`, `height`, `weight`:

- `age` и `age_years` несут одну и ту же информацию (идеальная коллинеарность) —
  для логистической регрессии это делает веса нестабильными и нечитаемыми.
- `height`, `weight` заменены на `bmi` ради меньшей коллинеарности и более чистой
  интерпретации (сознательный компромисс: BMI теряет часть информации о
  телосложении, но для baseline это оправдано).

**Итоговые 10 признаков:** `gender`, `ap_hi`, `ap_lo`, `cholesterol`, `gluc`,
`smoke`, `alco`, `active`, `age_years`, `bmi`.

## 4. Разбиение и защита от утечек

Разбиение `train_test_split(test_size=0.2, stratify=y, random_state=42)`:

- `stratify=y` сохраняет баланс классов (датасет сбалансирован ~50/50) в обеих
  частях;
- `random_state=42` — воспроизводимость.

**Правило защиты от утечки данных (data leakage):**

> Любой параметр, который **вычисляется из данных** (среднее и std для
> `StandardScaler`, медианы для заполнения пропусков, частоты категорий),
> считается **только на train**. Любое правило, заданное **извне** (медицинские
> границы очистки), можно применять до разбиения.

Поэтому очистка по доменным границам, выполненная до сплита, утечкой **не
является** (границы не выведены из данных), а масштабирование по всему датасету —
было бы утечкой: тест перестал бы быть «невиданными пациентами», и оценка
оказалась бы нечестно завышенной. Масштабирование выполняется внутри `Pipeline`,
который обучается строго на train-части каждого фолда.

## 5. Модели и метрики

**Зачем baseline.** Простая модель задаёт точку отсчёта: если сложная модель её не
бьёт — сложность не окупается или где-то ошибка.

**Почему ROC-AUC для сравнения моделей.** `recall` и `accuracy` зависят от порога
(0.5 по умолчанию), а порог мы будем менять. ROC-AUC измеряет качество
ранжирования при всех порогах сразу и потому пригоден для честного сравнения
моделей между собой. Порог настраивается отдельно (раздел 6).

Сравнение проводилось через 5-fold кросс-валидацию на train (ROC-AUC):

| Модель | ROC-AUC | Комментарий |
|---|---|---|
| Логистическая регрессия (baseline) | 0.792 | `StandardScaler` + `LogReg` |
| Random Forest (без ограничений) | 0.768 | переобучение: train ≈ 0.99, test ≈ 0.77 |
| Random Forest (`max_depth=6`, `min_samples_leaf=50`) | 0.797 | регуляризация вылечила переобучение |
| **CatBoost** | **0.799** | лучший результат, выбран финальной моделью |

**Выводы:**

- **Сложнее ≠ лучше.** Random Forest «из коробки» (0.768) проиграл простому
  логрегу (0.792) из-за переобучения — ровно та причина, по которой baseline
  обязателен. Ограничение глубины (`max_depth`, `min_samples_leaf`) подняло лес до
  0.797.
- **Потолок данных.** Все модели упираются в ~0.80 ROC-AUC. Признаки (давление,
  возраст, холестерин) просто не содержат больше информации — это ограничение
  данных, а не моделей.

Финальная модель **CatBoost** на отложенном тесте дала **ROC-AUC = 0.801**, что
совпадает с кросс-валидацией (0.799) — модель не переобучена и честно обобщает.

## 6. Выбор порога классификации

При пороге по умолчанию 0.5 CatBoost даёт recall по классу «болен» 0.70 и
**2039 ложноотрицательных** (FN — больные, отправленные домой как здоровые).

**Почему приоритет recall.** В медицине цена пропуска больного (FN) несопоставимо
выше цены ложной тревоги (FP): пропущенный диагноз — это риск для жизни, ложная
тревога — дополнительное обследование. Поэтому recall важнее accuracy и precision.

Порог — это **не математический, а медицинский/бизнес-выбор**. Так как задача —
**скрининг** (первичный отсев для направления на уточняющие процедуры), порог
снижен до **0.35**:

| Порог | recall (болен) | FN (пропущено) | FP (ложные тревоги) |
|---|---|---|---|
| 0.50 | 0.70 | 2039 | 1546 |
| 0.40 | 0.79 | 1428 | 2353 |
| **0.35 (выбран)** | **0.83** | **1125** | 2907 |

Снижение порога с 0.50 до 0.35 сократило число пропущенных больных с 2039 до
1125 (**~900 спасённых**), ценой роста ложных тревог. У снижения есть «дно»: при
слишком низком пороге recall → 1.0, но модель помечает больными почти всех,
precision рушится, и инструмент становится бесполезным. 0.35 — баланс, а не
крайность.

## 7. Анализ ошибок

Сравнение средних значений признаков у пропущенных больных (FN) и пойманных (TP),
порог 0.35:

| Признак | FN (пропущенные) | TP (пойманные) |
|---|---|---|
| `ap_hi` | 116 | 138 |
| `ap_lo` | 77 | 86 |
| `cholesterol` | 1.10 | 1.60 |
| `age_years` | 50.6 | 55.9 |
| `bmi` | 26.0 | 29.1 |

**Вывод.** Пропущенные больные — это пациенты с **нормальным давлением, нормальным
холестерином, моложе и стройнее**. По всем измеряемым признакам они выглядят как
здоровые, и модель закономерно не может их отличить. Ошибка не в модели, а в
**пределе признакового пространства**: доступные измерения не содержат сигнала для
этой подгруппы. Улучшить recall здесь можно только добавив новые признаки
(семейный анамнез, ЭКГ, биомаркеры), а не усложняя модель.

## 8. Интерпретация модели (SHAP)

- **Глобально** важнейшие признаки: `ap_hi`, `age_years`, `cholesterol`, `bmi`,
  `ap_lo`. Направление влияния совпадает с медициной (выше давление, возраст,
  холестерин → выше риск) — модель выучила **реальные закономерности, а не шум**,
  ей можно доверять.
- `smoke` и `alco` практически не влияют. Вероятная причина — самоотчётный
  характер данных и малое число курильщиков: не всякий «очевидно важный» признак
  реально работает в данных.
- **Локальный** анализ ложноотрицательных подтверждает раздел 7: у пропущенных
  больных все главные драйверы находятся на «здоровом» конце, и модель уверенно
  относит их к здоровым.

Две независимые линии анализа (статистика ошибок и SHAP) приходят к одному
выводу — это признак целостного понимания модели.

## 9. Развёртывание (FastAPI)

Модель упакована в REST-сервис (`app.py`) с эндпоинтом `POST /predict`.

**Дизайн входа.** Сервис принимает **сырые клинические данные** (возраст в днях,
рост, вес и т.д.), а `age_years` и `bmi` вычисляет **внутри** той же формулой, что
при обучении. Это защищает от **training/serving skew** — рассинхрона между тем,
как признак считался при обучении и в продакшене: рецепт признаков живёт в одном
месте, клиенту не нужно знать внутреннюю кухню.

**Артефакт.** В `models/cardio_model.joblib` сохранены одним словарём: обученная
модель, рабочий порог (0.35) и порядок признаков — всё, что нужно сервису для
честного предсказания.

**Пример запроса:**

```json
{
  "age": 22000, "gender": 2, "height": 165, "weight": 90,
  "ap_hi": 170, "ap_lo": 100, "cholesterol": 3, "gluc": 3,
  "smoke": 1, "alco": 0, "active": 0
}
```

**Ответ:**

```json
{ "prediction": 1, "probability": 0.896 }
```

На профиле здорового пациента сервис возвращает `{"prediction": 0, "probability": 0.055}`.
